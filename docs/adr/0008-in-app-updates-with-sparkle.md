# ADR-0008: In-app updates with Sparkle

- **Status:** Proposed
- **Date:** 2026-10-25
- **Deciders:** @iamAdarshh

## Context
To update Mullion today, users notice a new release on GitHub, download the DMG, quit Mullion, replace the app, and click *Open Anyway* again. Only Homebrew users get `brew upgrade`. [ADR-0002](0002-distribution-outside-app-store.md) and [ADR-0005](0005-dependencies.md) already named Sparkle as the candidate, on two conditions: its own ADR, and opt-in, because it adds network access to an app that promises none (CLAUDE.md rule 5, PRD NFR-3, SECURITY.md).

Constraints: no Developer ID; releases are signed with a self-signed certificate from v1.1.0 ([ADR-0007](0007-self-signed-release-certificate.md)), so an update keeps the Accessibility permission; public APIs only; the maintainer is new to Swift.

Sparkle's update validator (`SUUpdateValidator.m`, 2.x) accepts an update when **either** the archive's EdDSA signature is valid **or** its code signature matches the old app's. EdDSA keys are free and generated by Sparkle's `generate_keys`, so a Developer ID isn't required. Rectangle ships Sparkle the same way (`SUFeedURL`, `SUPublicEDKey`, `SUScheduledCheckInterval` in its Info.plist), and its Homebrew cask sets `auto_updates true`.

## Options considered
1. **Sparkle 2** (MIT).
   - Pros: the standard updater for apps outside the App Store; release notes, *Install and Relaunch* and scheduling built in; asks before checking automatically; EdDSA works without a Developer ID; the update replaces the app in place, so with ADR-0007 the permission survives.
   - Cons: a framework with helper tools to embed and sign; it needs `disable-library-validation` with a self-signed certificate (ADR-0007, confirmed in a spike); an EdDSA private key to keep safe; CI must sign each update and publish an appcast.
2. **Our own check against the GitHub Releases API**, then open the download page.
   - Pros: no dependency, a few dozen lines.
   - Cons: installing stays manual, with the Gatekeeper prompt every time; we'd own the UI, scheduling and failure handling; unauthenticated API calls are rate-limited.
3. **Homebrew only** (`brew upgrade`). Zero code, but only for Homebrew users, and nothing in the app tells anyone an update exists.

## Decision
We will add **Sparkle 2.10.0** (pinned exactly, through Swift Package Manager in `project.yml`) because it's the proven way to install an update in place, and it works without a Developer ID.

- **Opt-in network access.** Mullion contacts the network in exactly two cases:
  - when the user chooses *Check for Updates…*;
  - on a schedule, once the user has said yes to automatic checks. Sparkle asks on the second launch, and *Settings → General* has the same switch.

  `SUEnableAutomaticChecks` is not set, so nothing is checked before the user answers. System profiling stays off (`SUEnableSystemProfiling` = NO), so only a normal HTTPS request for the feed is sent.
- **Feed.** `SUFeedURL` = `https://github.com/iamAdarshh/Mullion/releases/latest/download/appcast.xml`. GitHub's "latest" skips drafts and pre-releases, so an update becomes visible only when its release is published, after the smoke test, and `-beta` builds never reach users.
- **Signing.**
  - The release workflow signs the ZIP with the EdDSA private key, stored as the `release` environment secret `SPARKLE_ED_PRIVATE_KEY` and backed up in the maintainer's password manager.
  - It generates `appcast.xml` from the ZIP and the CHANGELOG section, and uploads it as a release asset.
  - The public key goes in Info.plist as `SUPublicEDKey`.
- **Integration.** `SPUStandardUpdaterController` lives in the app target only (MullionCore stays dependency-free). The *Check for Updates…* menu item and the Settings switch follow the [updates spec](../features/updates.md).

## Consequences
- Positive: one-click updates that keep the Accessibility permission; release notes in the app; the Homebrew cask can set `auto_updates true`.
- Negative / accepted trade-offs:
  - Mullion is no longer "no network, ever". It's "no network unless you ask for updates": CLAUDE.md rule 5, PRD NFR-3, SECURITY.md and the README say so.
  - A second secret to keep safe: if the EdDSA key is lost, users of older versions can't take the next update and must install it by hand.
  - Sparkle's framework, its `Autoupdate` tool and `Updater.app` must all be signed with the release certificate.
- Follow-ups: the [updates spec](../features/updates.md); the release workflow steps; an end-to-end test that updates a signed build from a local appcast and checks the permission and Gatekeeper; manual test rows; `auto_updates true` in the cask.
